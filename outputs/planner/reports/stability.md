# Roster stability after a change

Generated by `python -m ree.cli planner stability`. Each seed solves a one-week roster of the 10-worker store, blocks two of its worker-days (the whole day, chosen at random from the shifts of that roster), and solves again twice: with the first roster as the stability reference and without it.

Seeds: 10.

| Measure | Mean over seeds [95 percent interval] |
|---|---|
| Assignments in the first roster | 48.1 [46.9, 49.2] |
| Changed, previous roster as reference | 28.0 [22.6, 33.9] |
| Changed, no reference | 53.1 [50.6, 55.9] |
| Uncovered staff-minutes, with reference | 3.0 [0.0, 9.0] |
| Uncovered staff-minutes, no reference | 9.0 [0.0, 27.0] |
| Checker errors, with reference | 0.0 [0.0, 0.0] |
| Checker errors, no reference | 0.0 [0.0, 0.0] |

Blocking 2 worker-days of a solved one-week roster of 48 assignments and solving again changes 28 assignments on average when the previous roster is given as the stability reference (a priced term of 15 per changed assignment) and 53 when it is not; a shift that moves to another day counts twice. The reference removes 251 of 531 changes (47%). A repair that moved only the blocked shifts and the few that take them over would change a handful of assignments, so at this search budget the solver does not stay close to the previous roster; a repair mode that fixes everything outside a neighbourhood of the change is not built.

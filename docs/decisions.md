# Decisions, defaults and assumptions

Every default the project relies on, with the reason and how to change it. Configuration paths refer to `config/default.yaml` (generated from `src/ree/config.py`; a test keeps the two in sync). Parameters of the simulated store are illustrative assumptions, not facts about any real store. Where the method document is ambiguous or disagrees with itself, the reading chosen is stated in the entry concerned (D-03, D-21, D-22, D-30).

## Store and calendar

- **D-01 Repository root.** The opened folder is the repository; the Python project is still called `retail-efficiency-engine`. Reason: no nested folder to confuse tools. Change: move the folder.
- **D-02 Opening hours.** Monday to Saturday 08:30 to 20:00, Sunday 08:30 to 12:30. Reason: an assumption; the method document does not fix the opening hours. Change: `store.opening`.
- **D-03 Rush windows.** Monday to Saturday 10:30 to 14:00 and 18:00 to 20:00; Friday and Saturday also 08:00 to 09:00 (in effect 08:30 to 09:00, because the store opens at 08:30); Sunday 11:00 to 12:30. Reason: the method document says "weekdays" for the 10:30 and 18:00 windows but calls Saturday busy, so the windows apply Monday to Saturday, and its 08:00 start on Friday and Saturday is earlier than the assumed opening, so it is clipped to the opening time. Change: `store.rush_windows`.
- **D-04 Lane groups and periods.** Zone A is registers 2, 3, 5, 6, 7; zone B is 8 to 15; register 1 is the priority lane; register 4 is the card-only lane; periods are peak and off-peak. Reason: the store layout described in the method document. Change: `store.priority_register`, `store.card_only_register`, `store.busy_zone_last_register`.
- **D-05 Seasons.** 28 December to 4 January: traffic x1.35, baskets x1.20; 25 August to 7 September: x1.20 and x1.10. Reason: the method document names the periods but not the effect, the multipliers are assumptions. Change: `store.seasonal`.
- **D-06 Default simulated window.** 12 weeks from Monday 2025-11-24, so Christmas is inside the window. Change: `simulator.start_date`, `simulator.n_weeks`.

## Simulated store (assumed parameters)

- **D-07 Timing model.** Per scanned item gap log-normal with mean 2.9 s / speed and sigma 0.35; fixed cost 25 s split 0.32 / 0.28 / 0.40 over the first, a random middle and the closing gap; hand-keyed items +0.7 s; tag removal uniform 5 to 7 s; loyalty card 8 s (60 percent of customers); vouchers 4 s each (0 to 3). Reason: plausible starting values for the simulated store. Change: `simulator.timing.*`.
- **D-08 Gap semantics.** The gap before an event is the work needed to produce it, so the first scan is the free start of the clock, and the closing gap carries one item-like cycle plus part of the fixed cost. The clock runs from the first scan or hand-keyed item to the payment press (`transaction_started` precedes the first scan by a customer-unloading delay that is never counted); gap events are scan, hand-keyed item, tag removal, voucher and loyalty scan, and exception events (void, manual entry, supervisor call, cheque, price check) never enter the gap sequence, they only flag the transaction. Reason: this makes the planted `alpha` exactly the intercept the engine fits. Change: not configurable (generator structure).
- **D-09 Interruptions per transaction.** "4 percent" customer delays (10 to 60 s) and "1.5 percent" interruptions (60 to 240 s) are read per transaction, one gap extended. Reason: read per gap, about a third of medium baskets and most big ones would be interrupted, which contradicts "rare outliers". Change: `simulator.timing.customer_delay_probability_per_transaction`, `...interruption_probability_per_transaction`.
- **D-10 Cashier population.** True speed sd 0.20 (log multiplier), peak effect sd 0.08, day-to-day session effect sd 0.03, correlation of speed with error propensity -0.30, 40 percent students (20 h) and 60 percent full-time (35 h), 12 percent newcomers hired inside the window whose speed is lowered by 0.15 to 0.40 and recovers with a 4-week time constant. Reason: plausible spreads; the correlation makes "fast" not imply "accurate". Change: `simulator.population.*`.
- **D-11 Baskets.** Class mixture per lane group (zone A 45/40/15, zone B 62/32/6, priority 50/37/13, card-only 80/19/1 percent small/medium/big) giving about 55/35/10 overall; 15 percent hand-keyed; 7 percent tagged with per-register heterogeneity. Reason: plausible shares for a large supermarket; heterogeneity lets v2 show its value. Change: `simulator.baskets.*`, `simulator.timing.tagged_share`.
- **D-12 Demand does not depend on cashier speed.** Idle time between customers is exponential with a mean set by lane utilisation (0.5 to 0.8) and a fixed nominal cycle, so a faster cashier serves more customers per hour. Reason: simple and stable. Consequence: this flatters the naive items-per-shift baseline in the balanced scenario; real queues that saturate would change it. Change: `simulator.traffic.*`.
- **D-13 Scheduler.** Shifts are continuous of about six hours with a 20-minute break, or split, and each shift is recorded as two sessions (before and after the break). Waves early, mid, late, split and Sunday with capacity limits so at most 15 registers are in use; registers 1 and 4 are staffed through the day; `biased` mode gives strong cashiers more peak hours, the card-only lane and smaller baskets and weak cashiers the reverse. Reason: a stand-in for Part 2. Change: `simulator.scheduler.*`.
- **D-14 Drawers.** A drawer is a register on a day for one worker; two workers on the same register-day share it with probability 0.25; 1.5 percent of drawers have an unclear owner. Rows of the cash sheet carry a drawer id so that the engine can split a drawer by cash share. Change: `simulator.scheduler.shared_till_probability`, `simulator.errors.unknown_owner_probability`.
- **D-15 Errors and cash.** Cash share 25 percent (none on the card-only lane); mistakes 0.8 percent of cash transactions times exp(0.6 x error propensity) with log-normal amounts (median 3 euros, sigma 0.8, random sign) and 0.15 euro natural noise per drawer; error voids 1.5 percent times exp(0.45 x propensity), customer voids 1.0 percent, supervisor voids 0.4 percent, void reason recorded for 70 percent; manual entries 1.2 percent times exp(0.35 x propensity). Change: `simulator.errors.*`.
- **D-16 Register software.** Unknown, so explicit supervisor, cheque and price-check events are off by default and the pause rule catches interruptions. Change: `simulator.timing.emit_exception_events`.

## Engine

- **D-17 Pause rule.** `T_idle` 15 s, `T_stop` 60 s, from the method document. Tuning from the store's own gaps (99.5th percentile of gaps in non-interrupted baskets, `T_stop` = max(60, 3 x `T_idle`)) is implemented and off by default; on the simulated store it gives about 20.7 s and 62 s. Change: `engine.pause.*`.
- **D-18 Hard 5 s stop baseline.** Every gap longer than 5 s is deleted (counted as zero), which is what the method document says would delete most of a slow cashier's time. Timings are floored at 0.5 s: 3.3 percent of transactions have every gap deleted, which made a log ratio infinite. Change: `engine.pause.hard_stop_seconds`.
- **D-19 What leaves speed scoring.** Transactions with a gap above `T_stop`, an explicit interruption event, a void or a manual entry are excluded from speed and kept for accuracy.
- **D-20 v1 bins.** Cells are (period, lane group, 5-item bin), last bin 80 items and more, at least 5 transactions per cashier and cell and 30 per store cell, cells weighted by the cashier's share. Change: `engine.speed.*`.
- **D-21 v2 regression.** The item count `n` is scan events plus hand-keyed events and `m` is the hand-keyed ones (the method document counts items as scan events, while its price list has `n` items and `m` hand-keyed items). One price list per lane group and period fitted by OLS (Huber selectable), per-cashier-and-period 3 MAD filter (a store-wide filter removed 75 percent of the slowest cashier's data), log ratios re-centred on the context median. The sanity check warns only when the 95 percent interval of delta is outside 5 to 7 s or of gamma above 1 s. Change: `engine.speed.regression`, `engine.speed.mad_threshold`.
- **D-22 Shrinkage and scale.** `n/(n+150)` toward the store reference (log ratios are already centred on the store median, so the method document's formula, which shrinks toward zero, and its text, which says toward the store average, agree); standard score over the rated cohort with the population standard deviation; `50 + 15 z`. A worker is rated in a period with at least 100 valid transactions and not provisional; workers below that threshold still get a score, heavily shrunk toward 50, marked `unrated`, and consumers place them at the cohort average. Change: `engine.speed.shrinkage_k`, `engine.min_transactions_rated`.
- **D-23 Z-score cap of plus or minus 3.** Not in the method document. Every z-score that enters a score is clipped at plus or minus 3, so one extreme observation (for example a very large discrepancy in a single week) can cost at most 27 accuracy points, or 9.5 combined points at peak. Reason: weekly cash errors are heavy-tailed and shrinkage alone does not protect a worker with one week of data; the cap makes "one bad week cannot define a person" true. It cannot fully protect either; see the tests. Change: `engine.combine.z_cap` (set a very large value to disable).
- **D-24 Accuracy.** Tolerance 1 euro per week, 12-week window, half-life 4 weeks, weights 0.6 / 0.4, shrinkage with k = 4 effective weeks for the cash error rate and k = 150 effective transactions for the void rate (the method document says "the same shrinkage" without naming the unit), error rate undefined below 500 euros of weighted cash (then the void rate alone is used). Drawers with an unclear owner are dropped; shared drawers are split by cash share. Change: `engine.accuracy.*`.
- **D-25 Voids.** Supervisor-requested and customer-change voids are excluded when the reason is recorded; unknown reasons count as errors.
- **D-26 Review flag.** Speed z at least 1.0 together with a void or manual-entry z at least 1.5 gives a text reason; it never changes a score. Change: `engine.review.*`.
- **D-27 Combination weights.** Speed 0.65 and accuracy 0.35 at peak, 0.5 and 0.5 off-peak (starting values from the method document). Change: `engine.combine.*`.
- **D-28 Intervals.** 90 percent, 200 bootstrap replicates, seed 7. Speed resamples whole sessions, accuracy resamples weeks, and every replicate recomputes the cohort mean and spread. Workers with under 2 weeks of cash data get the cohort spread around their own estimate. No inflation factor is applied. Measured: speed intervals are calibrated (SD ratio 1.05 to 1.11), the accuracy and combined intervals are about 1.2 to 1.4 times too narrow, and a 90 percent interval contains the replicate mean 78.7 percent of the time against 88.5 percent for a perfectly calibrated interval (`outputs/reports/results.md`). The tiers are conservative because of this. Change: `engine.intervals.*`.
- **D-29 Tiers.** A is the top 20 percent and C the bottom 20 percent of the eligible group; B in between. Eligible: interval at most 20 points wide, at least 4 weeks of data, at least 3 peers in the group. A or C is kept only when the whole interval clears the midpoint cutoff to the next tier, otherwise the worker is shown as B. Provisional workers form their own group. Change: `engine.tiers.*`, `engine.intervals.width_limit`.
- **D-30 Provisional label and tenure.** Under 4 weeks since the hire date. `hire_date` is read only by the pipeline, for this label and for keeping provisional workers out of the reference cohort; contract type is never read (tested). Newcomers are therefore scored on the same scale but not tiered against veterans.
- **D-31 Drivers.** Contributions in score points from speed by basket class, void rate and cash discrepancies; at least 1 point to be listed; at most 4 entries including the provisional and limited-data notes.
- **D-32 Reproducibility.** `computed_at` is the as-of time of the data; `model_version` combines the package version, a hash of the engine and store configuration and a hash of the engine source; wall-clock time exists only in the audit log; the scores file is written as UTF-8 with LF line endings.
- **D-33 Default speed method: v2 with OLS.** Chosen by the method document's rule ("the one that recovers their true order better") from `outputs/reports/results.md`: mean Spearman over the six scenarios 0.9859 against 0.9809 for v1 and 0.9857 for Huber; v2 is better or tied in every scenario. Change: `engine.speed.method`, `engine.speed.regression`.

## Experiments, fairness, API and screens

- **D-34 Experiment design.** Six methods compared on identical stores, 10 seeds per scenario (base seed 1000), 95 percent t-intervals over seeds, paired differences for comparisons, 0.005 Spearman as the smallest difference called practically relevant. Methods are scored per period against `true_speed` (off-peak) and `true_speed + peak_effect` (peak); the headline is the mean of the two; for the newcomer scenario a second target is reported, the pooled latent long-run skill, because newcomers speed up with tenure. The naive baseline is items per logged-in hour in the period (shift-length normalised). Change: `experiments.*`, `src/ree/experiments/scenarios.py`.
- **D-35 Calibration.** Replicates re-simulate fresh data for the same hidden cashiers (`simulator.replicate`); the target is the mean score on the other replicates; the benchmark accounts for that target's own noise.
- **D-36 Bias audit.** Scores are compared by contract type and tenure band at the same hidden skill (the speed actually shown for speed and combined scores, minus the error propensity for accuracy). Limits: 5 points for the group gap, 0.35 for the relative slope difference, at least 5 workers on each side, 10 stores in the experiment report. The test suite fails if the default store exceeds them. The report also repeats the speed-by-tenure audit with `engine.speed.shrinkage_k = 0` to show how much of the newcomer gap is shrinkage. Change: `fairness.*`.
- **D-37 API.** `GET /scores/ranking` is declared before `GET /scores/{worker_id}`. `min_confidence` turns low-confidence workers into unrated placements (cohort average, flagged) instead of dropping them. Appeals are stored in the store's SQLite file with the model version. No authentication: this is a demonstration service. Change: `src/ree/api/`.
- **D-38 Review screen.** Forms are avoided (plain widgets and buttons); appeals are written straight to the database; "regenerate" overwrites the store directory. Change: `src/ree/ui/review_app.py`.
- **D-39 Code documentation.** Public modules, classes and functions carry short plain-English docstrings where their purpose is not clear from the name; comments say why, not what. The method and every default are documented in the README and in `docs/`, not in the code. Change: not configurable.
- **D-40 Smoke command.** `python -m ree.cli smoke` (also `make smoke`) simulates 8 cashiers for 4 weeks, scores them twice with 60 bootstrap replicates and requires a byte-identical rerun and one audit row, probes the API in process (D-42), runs the six scenarios once at the reduced size, and loads every screen headlessly. The experiment step passes when v2 recovers at least 0.8 of the hidden speed order, beats the hard 5 s stop, and the naive baseline is beaten under biased assignment. The thresholds are loose on purpose: the check is for a broken install, not a measurement. Change: the `SMOKE_*` constants in `src/ree/experiments/run_all.py`.
- **D-41 Review screen script.** `src/ree/ui/review_app.py` calls `main()` only when run as a script, so importing it (for the list of views) has no side effects; Streamlit and its test harness both run a script as `__main__`.
- **D-42 Packaging.** Runtime dependencies are exactly what `src/ree` imports (a test checks every third-party import against `project.dependencies` and that no module imports a test client). Dev tools (pytest, hypothesis, ruff, httpx2) are declared twice: as a PEP 735 `dev` dependency group, which `uv sync` installs, and as the `dev` extra, which `pip install -e ".[dev]"` installs; a test keeps the two lists equal. The smoke command probes the API in process through the ASGI interface (`ree.api.probe`) instead of Starlette's `TestClient`, because the client moved from httpx to httpx2 and a plain `uv sync` (no dev tools) failed with "The starlette.testclient module requires the httpx2 package"; a runtime command should not need an HTTP client library, and calling the app through ASGI still exercises routing, validation and serialisation. `uv.lock` is committed so `uv sync` installs the versions that were tested. Every Makefile target is a one-line wrapper over `python -m ree.cli <command>`, so each target also runs without GNU make, which is not installed on the Windows development machine. Change: `pyproject.toml`, `Makefile`.

The shift planner (Part 2) keeps its own decisions in `docs/planner_decisions.md`.
